## 1. Цель

Перенести модель данных из ЛР2 в PostgreSQL руками, на SQL, без EF. Что для этого нужно:

- таблицы справочников, пользователей и заявок на ремонт со связями (PK, FK);
- `CHECK` на четыре статуса и индексы;
- учебные данные во всех четырёх статусах;
- запросы с фильтром, сортировкой, `JOIN` и `GROUP BY`;
- проверка, что запись на месте после перезапуска PostgreSQL.

## 2. Что сделали

1. **`db/schema.sql`** — четыре таблицы по `docs/data-model.md`. Имена в SQL в `snake_case` и совпадают с JSON API ЛР8: `equipmentId` ↔ `equipment_id`, `assigneeUserId` ↔ `assignee_user_id`.
   - `areas` — участки цеха (`name` UNIQUE).
   - `equipment` — справочник главного объекта (на курсе — `sites`). Поля `inventory_number` UNIQUE, `name`, `area_id` FK → `areas`.
   - `users` — `login` UNIQUE, `full_name`, `role` с `CHECK` на четыре роли, `password_hash` (пока `NULL`, вход — ЛР11).
   - `work_orders` — главный объект (на курсе — `tickets`). Поля: `id` PK, `number` UNIQUE, `title`, `description`, `status`, `equipment_id` FK, `created_by_user_id` FK, `assignee_user_id` FK `NULL`, `created_at`, `updated_at`.
2. **Ограничения `work_orders`:**
   - `status` — `CHECK (status IN ('New', 'InProgress', 'Closed', 'Cancelled'))`, по умолчанию `'New'`;
   - длины `title` 5–80 и `description` 10–500 после `btrim`, те же правила ФТ-3, что на клиенте и сервере;
   - `work_orders_work_needs_assignee_chk` — `InProgress` и `Closed` только с назначенным исполнителем. Это правило ЛР8 (там `409`) продублировано в базе;
   - все FK с `ON DELETE RESTRICT`: оборудование или пользователя с заявками удалить нельзя.
3. **Индексы** (у каждого в файле комментарий «зачем»):
   - `work_orders_status_idx` — фильтр по статусу (обязательный);
   - `work_orders_equipment_id_idx` — фильтр по станку и JOIN (обязательный, FK справочника);
   - `work_orders_assignee_user_id_idx` — «Мои заявки» слесаря (ФТ-12);
   - `work_orders_created_at_idx` — сортировка «новые сверху»;
   - `equipment_area_id_idx` — JOIN оборудования с участком.
4. **Повторный запуск схемы.** В начале `schema.sql` стоит `DROP TABLE IF EXISTS` только для таблиц проекта, в порядке, обратном зависимостям. Это учебное пересоздание схемы, а не команда приложения: `DELETE` в REST API по-прежнему нет.
5. **`db/seed.sql`** — в одной транзакции:
   - 3 участка, 12 единиц оборудования и 6 пользователей — те же, что в `backend/Data/ReferenceData.cs`;
   - 8 заявок во всех четырёх статусах.
   - Ссылки ищутся по инвентарному номеру и логину, а не по жёстко заданным `id`. Паролей в seed нет.
6. **`db/queries.sql`** — пять запросов и три проверки ограничений. Проверки — каждая в `BEGIN … ROLLBACK`, поэтому ошибочные строки в данных не остаются.
7. **`SET client_encoding = 'UTF8'`** в начале каждого файла: на Windows `psql` иначе читает UTF-8 файл как WIN1251 и портит кириллицу.
8. **`.gitignore`** — добавлены `*.dump`, `*.backup`, `.pgpass`: дампы и файл паролей PostgreSQL в Git не попадут.
9. **README** — раздел «База данных»: команды `psql` и шаги в pgAdmin, пересоздание, пароль не хранится в файлах.

## 3. Запуск

Проверено на PostgreSQL 16, учебная база `toir_workshop` (не служебная `postgres`):

```bash
createdb -U postgres toir_workshop
psql -U postgres -d toir_workshop -f db/schema.sql
psql -U postgres -d toir_workshop -f db/seed.sql
psql -U postgres -d toir_workshop -f db/queries.sql
```

Вывод `seed.sql`:

```text
SET
BEGIN
INSERT 0 3
INSERT 0 12
INSERT 0 6
INSERT 0 8
COMMIT
```

Повторный запуск `schema.sql` на уже заполненной базе проходит без ошибок: таблицы удаляются и создаются заново.

JOIN equipment   AS e ON e.id = w.equipment_id

## 5. Проверка ограничений

| Попытка | Ожидание | Факт |
|---------|----------|------|
| Вставить заявку со статусом `Done` | отказ CHECK | `ERROR: new row for relation "work_orders" violates check constraint "work_orders_status_check"` |
| Вставить заявку с `equipment_id = 999` | отказ FK | `ERROR: insert or update on table "work_orders" violates foreign key constraint "work_orders_equipment_id_fkey"`, `DETAIL: Key (equipment_id)=(999) is not present in table "equipment".` |
| Перевести `ЗР-2026-0006` (без исполнителя) в `InProgress` | отказ CHECK | `ERROR: ... violates check constraint "work_orders_work_needs_assignee_chk"` |
| После трёх проверок | данные не изменились | `total_work_orders = 8` |

Все проверки выполнены в `BEGIN … ROLLBACK`, поэтому ошибочных строк в рабочих данных нет.

PostgreSQL проверяет CHECK-ограничения в алфавитном порядке имён. Поэтому правило про исполнителя названо `work_orders_work_needs_assignee_chk`, чтобы оно проверялось после `work_orders_status_check`. Тогда строка `Done` отклоняется именно ограничением статуса, и ошибку легко прочитать.

## 6. Данные переживают перезапуск PostgreSQL

```text
INSERT INTO work_orders (number, title, description, equipment_id, created_by_user_id) VALUES ('ЗР-2026-0009', 'Проверка после перезапуска', … ) RETURNING id, number, status;
 id |    number    | status
----+--------------+--------
 11 | ЗР-2026-0009 | New

$ service postgresql restart
 * Restarting PostgreSQL 16 database server   ...done.

SELECT id, number, title, status, created_at FROM work_orders WHERE number = 'ЗР-2026-0009';
 id |    number    |           title            | status |          created_at
----+--------------+----------------------------+--------+-------------------------------
 11 | ЗР-2026-0009 | Проверка после перезапуска | New    | 2026-10-23 14:01:28.590557+03
```

Строка на месте после перезапуска. Видно и то, что `id` и `number` — разные поля. Отменённые проверочные вставки (`ROLLBACK`) уже взяли значения 9 и 10 из последовательности, поэтому `id = 11`, а человеческий номер — `ЗР-2026-0009`. Пропуски в `id` нормальны: это машинный ключ, его не диктуют людям.

На Windows то же самое проверяется перезапуском службы `postgresql-x64-<версия>` в «Службах» или перезагрузкой компьютера.

## 7. Сверка с моделью ЛР2 и API ЛР8

| ЛР2 / JSON API | SQL | Совпадает |
|----------------|-----|-----------|
| `WorkOrder.id`, `number` | `work_orders.id` PK, `number` UNIQUE | да |
| `title`, `description` | `title`, `description` + CHECK длины | да |
| `status` (4 кода) | `status` + CHECK 4 кода | да |
| `equipmentId` | `equipment_id` FK → `equipment` | да |
| `createdByUserId`, `assigneeUserId` | `created_by_user_id`, `assignee_user_id` FK → `users`, исполнитель `NULL` | да |
| `createdAt`, `updatedAt` | `created_at`, `updated_at` `timestamptz` | да |
| `Equipment.areaId` → `Area` | `equipment.area_id` FK → `areas` | да |
| `User.passwordHash` (обязательный) | `password_hash` пока `NULL` | временно: вход и хеши появятся в ЛР11, тогда поле станет `NOT NULL` |

## 8. Ответы для защиты

1. **Зачем индекс по статусу?** Самые частые запросы — список с фильтром по статусу (`WHERE status = 'New'`) и сводка начальника цеха по статусам. Индекс работает как закладка в книге: база не перебирает все строки, а сразу находит нужные. На 8 строках разницы не видно, а на тысячах заявок за годы работы цеха она будет заметна. По описанию индекса нет: по нему не ищут, а лишний индекс замедляет каждую вставку.
2. **Почему название станка — не текст в заявке?** Это 3НФ. Название и участок хранятся один раз в `equipment`, а в заявке только `equipment_id`. Переименовали станок или перенесли его на другой участок — меняется одна строка, и все заявки сразу показывают новое название через JOIN. FK к тому же не даёт сослаться на несуществующий станок.
3. **Чем JOIN отличается от GROUP BY?** `JOIN` склеивает строки разных таблиц: к заявке приписывает название станка и участка, число строк остаётся тем же. `GROUP BY` сворачивает много строк одной таблицы в группы и считает агрегат: сколько заявок в каждом статусе, получается 4 строки вместо 8. Их можно сочетать, как в запросе 4.4.
