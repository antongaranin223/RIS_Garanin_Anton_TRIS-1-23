## 1. Цель

Реализовать на сервере REST главного объекта — заявки на ремонт `/api/work-orders`:

- создание (`201`);
- чтение списка и одной заявки;
- отдельное назначение слесаря и отдельная смена статуса.

Ответы должны быть предсказуемыми: `201` / `400` / `404` / `409`. Неожиданный сбой пишется в лог одной строкой, а клиент получает безопасный `500` без stack trace. Данные пока в памяти.

## 2. Что сделали

Имена взяты из контракта ЛР2 (`docs/api-contract.md`):

| Курс | Тема |
|------|------|
| `/api/tickets` | `/api/work-orders` |
| `siteId` | `equipmentId` |
| `Ticket` | `WorkOrder` |

Статусы — `New`, `InProgress`, `Closed`, `Cancelled`.

1. **DTO** (`backend/Dtos/`):
   - `CreateWorkOrderRequest` — только `title`, `equipmentId`, `description`. Проверки по ФТ-3: `title` 5–80 символов и `description` 10–500 символов (обе после `Trim`), `equipmentId` — целое больше 0.
   - `AssignWorkOrderRequest` — только `assigneeUserId`.
   - `ChangeWorkOrderStatusRequest` — только `status`, допустимы четыре кода.
   - `WorkOrderResponse` — ответ сервера с ФИО исполнителя. ФИО собирается из справочника, в заявке хранится только `assigneeUserId`.
   - `id`, `number`, `status`, автора и исполнителя клиент при создании не задаёт. Если прислать `"status": "Closed", "id": 999`, сервер их игнорирует.
2. **Модели** (`backend/Models/`): `WorkOrder` из ЛР7, `AppUser` с ролями и `Equipment`.
3. **Справочники в памяти** (`backend/Data/ReferenceData.cs`): оборудование 1–12 и пользователи. Пользователь 1 и 4 — мастера, 2 — механик, 3 — начальник цеха, 5 и 6 — слесари. Сервер проверяет по ним `equipmentId` и `assigneeUserId`.
4. **Сервис** `InMemoryWorkOrderService`:
   - список в памяти и счётчик `id`; номер вида `ЗР-2026-0001`;
   - `lock`, потому что сервис singleton и запросы приходят параллельно;
   - правила процесса в одном месте — метод `CheckTransition` с таблицей переходов из `docs/data-model.md` §6;
   - ожидаемые отказы возвращаются как `ServiceResult` (`Validation` / `NotFound` / `Conflict`), без исключений.
5. **Контроллер** `WorkOrdersController` — тонкий: принимает HTTP, вызывает сервис и превращает `ServiceResult` в `200` / `201` / `400` / `404` / `409`. Пять маршрутов, `DELETE` нет.
6. **Текущий пользователь** до ЛР11 передаётся заголовком `X-User-Id`. Он обязателен для `POST` и `PATCH …/status`, без него — `400`. По совету карточки ЛР8 чужие действия возвращают `409`, а не `403`.
7. **Единый вид ошибок** — `ProblemDetails`. У `400` формат `ValidationProblemDetails` с заголовком «Ошибка проверки полей» и `errors` по именам полей JSON (`title`, `equipmentId`…), как ждёт клиент из ЛР6. Технические сообщения System.Text.Json заменены понятным текстом: `Infrastructure/ValidationResponses.cs`.
8. **Неожиданный сбой:**
   - в `Create` при исключении — одна строка лога `CreateWorkOrder failed; equipmentId=…; error=<тип>`, клиенту безопасный `500`;
   - для остальных адресов страховка `UseExceptionHandler`: тоже одна строка в лог и `500` без stack trace даже в Development;
   - учебный сбой включается заголовком `X-Simulate-Failure: 1`, который работает **только в Development**. Карточка ЛР8 разрешает такой переключаемый флаг; он описан в README.
9. **Коллекция Postman** `docs/api-collection/work-orders.postman_collection.json`: 15 запросов со встроенными проверками кодов и полей. В README описано, как импортировать её и какой базовый URL.
10. **`backend/backend.http`** — те же основные запросы для VS Code / Rider.

## 3. Маршруты и коды

| Метод и путь | Успех | Отказы |
|---|---|---|
| `GET /api/work-orders` | `200`, массив (пустой — `[]`) | — |
| `GET /api/work-orders/{id}` | `200` | `404` нет заявки |
| `POST /api/work-orders` | `201` + `Location`, `id`, `number`, `status: "New"` | `400` поля / нет `X-User-Id`; `409` создаёт не мастер и не механик |
| `PATCH /api/work-orders/{id}/assignee` | `200`, статус остаётся `New` | `400` не слесарь; `404`; `409` заявка не в `New` |
| `PATCH /api/work-orders/{id}/status` | `200` | `400` неизвестный код; `404`; `409` запрещённый переход |

Правила переходов (`409`, если нарушены):

| Переход | Кто может |
|---------|-----------|
| `New` → `InProgress` | только назначенный слесарь; **без исполнителя — 409** |
| `InProgress` → `Closed` | только назначенный слесарь |
| `New` → `Cancelled` | механик цеха или мастер — автор заявки |
| любой другой (`New` → `Closed`, из `Closed` / `Cancelled`) | никто |

## 5. Доказательство лога неожиданной ошибки

Запрос `15` коллекции: `POST /api/work-orders` с корректными полями и заголовком `X-Simulate-Failure: 1`. Сервис выбрасывает `InvalidOperationException` после успешной валидации.

**Что видит разработчик** — консоль `dotnet run`, одна строка: операция, ключ и тип ошибки. Тела запроса целиком в ней нет:

```text
fail: Backend.Controllers.WorkOrdersController[0]
      CreateWorkOrder failed; equipmentId=2; error=InvalidOperationException
```

**Что видит клиент** — безопасный `ProblemDetails` без stack trace, путей к файлам и тела запроса:

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"Не удалось обработать запрос","status":500,"detail":"Произошла внутренняя ошибка сервера. Попробуйте позже.","traceId":"00-2ab1…-00"}
```

Ожидаемые отказы (`400` / `404` / `409`) — не аварии. `409` пишется в лог кратко, на уровне `info`: `WorkOrder action rejected (409): Нельзя перевести в ремонт: исполнитель не назначен`.

Учебный сбой оставлен как флаг, а не как «бросок в коде». Он срабатывает только при заголовке `X-Simulate-Failure: 1` и только в среде Development; в Production заголовок игнорируется. Флаг описан в README.

## 7. Ответы для защиты

1. **Почему назначение и статус — два PATCH?** Это разные действия разных людей. Назначает механик, статус двигает слесарь. Права и правила у них свои: назначить можно только в `New`, «в ремонт» — только назначенному. Общий «обновить всё» позволил бы одним запросом сменить и исполнителя, и статус в обход правил. Кроме того, отказ было бы трудно объяснить.
2. **Чем `400` отличается от `409`?** `400` — сам запрос плохой: короткий заголовок, не число, неизвестный код статуса. Его можно исправить, не глядя на состояние заявки. `409` — запрос правильный, но противоречит текущему состоянию процесса: нельзя «в ремонт» без исполнителя, нельзя менять выполненную заявку.
3. **Почему пустой список — `200`, а не `404`?** Адрес `/api/work-orders` существует, и запрос выполнен успешно: заявок просто ноль. `404` значит «нет такого ресурса», например заявки с `id` 999999.
4. **Что видят клиент и разработчик при неожиданном сбое?** Клиент получает `500` и короткий `ProblemDetails` «Не удалось обработать запрос», без stack trace, путей и тела запроса: это и безопасность, и понятность. Разработчик видит в консоли одну строку: какая операция, какой ключ (`equipmentId`), какой тип ошибки. Тело запроса целиком в лог не пишется, чтобы туда не попали будущие токены и персональные данные.

**DTO — не строка таблицы.** Сущность `WorkOrder` хранит всё: `id`, номер, статус, автора, даты. DTO создания описывает только то, что человеку разрешено прислать по сети. Поэтому клиент физически не может задать себе `status: Closed`.
