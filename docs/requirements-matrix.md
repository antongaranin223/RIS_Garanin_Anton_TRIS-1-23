## 1. Три обязательных критерия ЛР1

| Требование ЛР1 | Поле или сущность | Запрос | Успех / отказ | Критерий |
|----------------|-------------------|--------|---------------|----------|
| Мастер участка создаёт заявку на ремонт (ФТ-2, ФТ-3, UC-1) | `WorkOrder`: `title`, `equipmentId` (FK → `Equipment`), `description`; сервер ставит `id`, `number`, `status = New`, `createdByUserId` | `POST /api/work-orders` | `201`, `number: ЗР-2026-NNNN`, `status: New`; неверные поля — `400` | **Критерий 1.** Создать объект |
| Механик цеха назначает слесаря-ремонтника отдельным действием (ФТ-4) | `WorkOrder.assigneeUserId` (FK → `User`, роль `Fitter`); `status` не меняется | `PATCH /api/work-orders/{id}/assignee` | `200`, исполнитель указан, статус `New`; не механик — `403` | **Критерий 2.** Назначить исполнителя |
| Назначенный слесарь переводит свою заявку в ремонт (ФТ-5, ФТ-8) | `WorkOrder.status`: `New` → `InProgress`; проверка `assigneeUserId` = текущий пользователь | `PATCH /api/work-orders/{id}/status` с `{ "status": "InProgress" }` | `200`, статус «В ремонте»; другой слесарь — `403` | **Критерий 3.** Исполнитель перевёл в работу |

## 2. Остальные требования ЛР1

| Требование ЛР1 | Поле или сущность | Запрос | Ожидаемый ответ |
|----------------|-------------------|--------|-----------------|
| ФТ-1. Вход, имя и роль в шапке | `User`: `login`, `passwordHash`, `fullName`, `role` | `POST /api/auth/login`, `GET /api/auth/me` | `200` + токен и пользователь; неверный пароль — `401` |
| ФТ-2. Выбор станка из справочника при создании | `Equipment`: `id`, `inventoryNumber`, `name`, `areaId` → `Area.name` | `GET /api/equipment` | `200`, массив или `[]` |
| ФТ-3. Проверка полей при создании | `title` 5–80, `equipmentId` существует, `description` 10–500 | `POST /api/work-orders` | `400` с `errors` по полям, заявка не создаётся |
| ФТ-4. Список слесарей для назначения | `User` с `role = Fitter` | `GET /api/users?role=Fitter` | `200`, массив; не механик — `403` |
| ФТ-6. Слесарь завершает ремонт | `status`: `InProgress` → `Closed` | `PATCH /api/work-orders/{id}/status` | `200`, «Выполнена»; дальнейшие изменения — `409` |
| ФТ-7. Отмена новой заявки | `status`: `New` → `Cancelled`; `createdByUserId` для мастера | `PATCH /api/work-orders/{id}/status` с `Cancelled` | `200`, «Отменена»; строка не удаляется |
| ФТ-8. Запрет: чужая заявка слесаря | `assigneeUserId` ≠ текущий пользователь | `PATCH /api/work-orders/{id}/status` | `403`, «Нет прав на изменение этой заявки» |
| ФТ-9. Запрет: назначает только механик | `User.role` ≠ `Mechanic` | `PATCH /api/work-orders/{id}/assignee` | `403` |
| ФТ-10. Запрет: недопустимые переходы | `status` и таблица переходов в [модели](data-model.md#6-статусы-и-переходы) | `PATCH /api/work-orders/{id}/status` | `409` |
| ФТ-11. Сводка начальника цеха с фильтрами | `status`, `equipmentId` | `GET /api/work-orders?status=…&equipmentId=…` | `200`, массив или `[]` |
| ФТ-12. «Мои заявки» слесаря | `assigneeUserId` = текущий пользователь | `GET /api/work-orders?mine=true` | `200`, массив или `[]` |
| Просмотр одной заявки | `WorkOrder.id` | `GET /api/work-orders/{id}` | `200`; нет такого `id` — `404` |
| НФТ-1. Данные переживают перезапуск | все таблицы в PostgreSQL | — | после рестарта `GET /api/work-orders` отдаёт те же записи |
| НФТ-2. Права на сервере | `User.role`, `createdByUserId`, `assigneeUserId` | все пути, кроме входа | без входа — `401`, без роли — `403` |
| НФТ-5. Пароли только хешем | `User.passwordHash` | `POST /api/auth/login` | хеш в ответах API не возвращается |

Каждое требование ЛР1 имеет строку: модель и API покрывают все ФТ-1…ФТ-12 и проверяемые через API НФТ.
