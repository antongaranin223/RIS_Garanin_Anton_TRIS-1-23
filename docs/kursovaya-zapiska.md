## Введение

В механосборочном цехе о неисправности станка мастер участка сообщает устно или в бумажном журнале. Механик цеха распределяет работу между слесарями «по памяти», а начальник цеха узнаёт, какие станки стоят, только обойдя участки. Из-за этого заявки теряются, двое слесарей приходят к одному станку, а время простоя никто не фиксирует.

**Цель работы** — разработать веб-информационную систему «ТОиР-Цех», которая ведёт заявку на ремонт конкретной единицы оборудования от создания до выполнения, хранит её в базе данных и разграничивает действия по ролям.

**Задачи:**

1. Проанализировать процесс и сформулировать требования (ЛР1).
2. Спроектировать архитектуру, модель данных и программный интерфейс (ЛР2).
3. Разработать клиентскую часть на Vue 3 (ЛР3–ЛР6, ЛР12).
4. Разработать серверную часть на ASP.NET Core Web API (ЛР7–ЛР8).
5. Спроектировать базу PostgreSQL и подключить её через EF Core с миграциями (ЛР9–ЛР10).
6. Реализовать вход, хранение паролей и проверку прав на сервере (ЛР11).
7. Собрать стенд, проверить критерии приёмки и описать поставку (ЛР12–ЛР13).

## 1. Анализ и требования

**Предметная область.** Техническое обслуживание и ремонт (ТОиР) оборудования цеха: токарные и фрезерные станки с ЧПУ, прессы, сборочные стенды. Процесс начинается с отказа или плановой потребности и заканчивается выполненным ремонтом. Автоматизация нужна, чтобы у каждой заявки были номер, ответственный и состояние, видимые всем участникам.

**Главный объект** — заявка на ремонт / ТО (`work order`). **Справочник** — оборудование, на которое ссылается заявка (`equipmentId`).

**Роли:**

| Роль | Создаёт | Назначает | Меняет статус |
|------|---------|-----------|---------------|
| Мастер участка | да | нет | отменяет только свою заявку в «Новая» |
| Механик цеха | да | да | отменяет заявку в «Новая» |
| Слесарь-ремонтник | нет | нет | «В ремонте» и «Выполнена» — только своей заявки |
| Начальник цеха | нет | нет | нет, только просмотр |

**Граница MVP.** В семестр вошло ядро — заявка на ремонт и её путь «Новая → В ремонте → Выполнена / Отменена». Паспорта оборудования, графики ППР, склад запчастей, интеграции и отчёты по простоям вынесены в запас ВКР (глава 7).

**Требования:** 12 функциональных (ФТ-1…ФТ-12) и 5 нефункциональных (НФТ-1…НФТ-5), пользовательские истории.

**Три обязательных критерия приёмки:**

| № | Дано | Когда | Тогда |
|---|------|-------|-------|
| 1 | мастер участка вошёл | заполнил заголовок, оборудование, описание и отправил форму | заявка создана в статусе «Новая» с номером `ЗР-ГГГГ-NNNN` |
| 2 | заявка в «Новая», механик цеха вошёл | выбрал слесаря и нажал «Назначить» | исполнитель сохранён, статус остался «Новая» |
| 3 | назначенный слесарь вошёл | нажал «В ремонт» | статус «В ремонте»; другой слесарь получает отказ 403 |

## 2. Проектирование и архитектура

**Архитектура web-ИС семестра** — три узла:

```text
Браузер: Vue 3 (Vite)  ──HTTP/JSON + JWT──►  ASP.NET Core Web API  ──EF Core / Npgsql──►  PostgreSQL
http://localhost:5173                        http://localhost:5000                        localhost:5432, toir_workshop
```

Браузер не обращается к базе напрямую. Пароль базы знает только сервер, а все правила (вход, роли, поля, переходы статусов) проверяет API.

**Модель данных** — четыре таблицы в третьей нормальной форме:

| Таблица | Назначение | Ключи |
|---------|------------|-------|
| `areas` | участки цеха | PK `id`, UNIQUE `name` |
| `equipment` | оборудование: инвентарный номер, название | PK `id`, UNIQUE `inventory_number`, FK `area_id → areas` |
| `users` | пользователи: логин, ФИО, роль, хэш пароля | PK `id`, UNIQUE `login`, CHECK роли |
| `work_orders` | заявки | PK `id`, UNIQUE `number`, FK `equipment_id`, `created_by_user_id`, `assignee_user_id`; CHECK четырёх статусов и длины полей |

Решения модели:

- `id` (машинный ключ) и `number` (`ЗР-2026-0001`, для людей) — разные поля.
- Название участка хранится только в `areas`: заявка → станок → участок.
- **Назначение ≠ статус:** `assignee_user_id` и `status` меняются разными действиями.
- Четыре статуса — `New`, `InProgress`, `Closed`, `Cancelled`. Переходы описаны таблицей, а в БД стоит CHECK: в «В ремонте» и «Выполнена» без исполнителя заявка попасть не может.

**Программный интерфейс** — REST, главный ресурс `/api/work-orders`. Создание — `POST`, назначение и смена статуса — два отдельных `PATCH`. `DELETE` нет: отмена — это статус.

**Артефакты:**

- `docs/architecture.md` — схема трёх узлов, кто за что отвечает, почему браузер не ходит в БД;
- `docs/data-model.md` — словарь, сущности, ER-диаграмма, проверка 3НФ, статусы и переходы;
- `docs/api-contract.md` — таблица API, примеры JSON, коды ответов;
- `docs/requirements-matrix.md` — требование → экран → API → таблица.

## 4. Сервер и программный интерфейс (API)

**Стек:**

- ASP.NET Core Web API на .NET 10;
- контроллеры с атрибутами `[ApiController]`;
- OpenAPI + Swagger UI.

**Слои:**

| Слой | Файлы | Ответственность |
|------|-------|-----------------|
| Контроллеры | `backend/Controllers/WorkOrdersController.cs`, `AuthController.cs`, `ReferenceController.cs` | принять HTTP, проверить DTO, превратить результат сервиса в код ответа. «Тонкие»: правил процесса нет |
| DTO | `backend/Dtos/*.cs` | что клиент может прислать (`title`, `equipmentId`, `description`; не `id`, не `status`) и что получит |
| Сервис | `backend/Services/IWorkOrderService.cs`, `EfWorkOrderService.cs`, `ServiceResult.cs` | правила: кто создаёт, кого можно назначить, таблица переходов статусов, «своя / чужая заявка», выдача номера |
| Данные | `backend/Data/AppDbContext.cs` | EF Core, глава 5 |

**Коды ответов:**

| Код | Когда |
|-----|-------|
| `200` | чтение, назначение, смена статуса |
| `201` + `Location` | создание |
| `400` | поля не прошли проверку (`ValidationProblemDetails` с `errors` по полям) |
| `401` | не вошёл |
| `403` | нет прав |
| `404` | нет записи |
| `409` | действие противоречит состоянию заявки |
| `500` | непредвиденный сбой: безопасный ответ без stack trace, одна строка в логе |

**Два PATCH:**

- `PATCH /api/work-orders/{id}/assignee` — только механик, только в `New`, статус не меняет;
- `PATCH /api/work-orders/{id}/status` — переход по таблице, права зависят от перехода и от того, чья заявка.

**Пример успешного и отказного ответа:**

```text
POST /api/work-orders  {"title":"Люфт шпинделя токарного станка","equipmentId":3,"description":"…"}
→ 201  {"id":1,"number":"ЗР-2026-0001","status":"New","assigneeUserId":null, …}

PATCH /api/work-orders/1/status  {"status":"Closed"}   (токен другого слесаря)
→ 403  {"title":"Нет прав на изменение этой заявки: она назначена другому слесарю","status":403}
```

## 5. База данных

**СУБД** — PostgreSQL 16.

**SQL-скрипты ЛР9** в `db/`:

- `schema.sql` — таблицы, PK, FK, CHECK, индексы;
- `seed.sql` — учебные данные;
- `queries.sql` — фильтр, JOIN, GROUP BY, проверки ограничений.

Это справочная схема и примеры запросов.

**Нормализация.** 3НФ на справочниках: заявка ссылается на `equipment_id`, станок — на `area_id`, исполнитель — на `users.id`. Статусы ограничены `CHECK (status IN ('New','InProgress','Closed','Cancelled'))`.

**EF Core.** `backend/Data/AppDbContext.cs` явно сопоставляет классы `WorkOrder`, `Equipment`, `Area`, `AppUser` с таблицами и столбцами `schema.sql`: имена в snake_case, те же CHECK, FK `ON DELETE RESTRICT`, индексы. Провайдер — Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3.

**Миграции в Git** (`backend/Migrations/`):

| Миграция | Что делает |
|----------|------------|
| `20261107071750_InitialCreate` | четыре таблицы, ограничения, индексы; справочники: 3 участка, 12 единиц оборудования, 6 пользователей |
| `20261107073927_AddPasswordHashes` | хэши паролей пользователей, `password_hash NOT NULL` |

Схема создаётся одной командой `dotnet ef database update`. Ручной `schema.sql` для приложения не нужен.

**Сохранность (НФТ-1).** Заявка создана, назначена и переведена в ремонт. Затем API остановлен и запущен заново новым процессом, и заявка на месте с тем же `id`, статусом и исполнителем. Проверено в ЛР10, ЛР12 и на предзащите ЛР13.

**Секрет подключения не в репозитории.** Строка подключения с паролем хранится в `dotnet user-secrets` (профиль пользователя) или в переменной окружения `ConnectionStrings__Default`. В `backend/appsettings.json` — пустой ключ. Поиск настоящего пароля по репозиторию даёт 0 совпадений.

## 6. Безопасность и тестирование

**Аутентификация.**

- Вход по логину и паролю — `POST /api/auth/login`.
- Сервер выдаёт учебный JWT (HMAC-SHA256, 8 часов) с id, ФИО и ролью. Клиент передаёт его в заголовке `Authorization: Bearer`.
- Ключ подписи `Jwt:Key` — секрет вне Git.
- Файлы: `backend/Auth/`, `backend/Controllers/AuthController.cs`, `backend/Program.cs`.

**Авторизация.** Права проверяет сервер (НФТ-2) в два уровня:

- `[Authorize]` и `[Authorize(Roles = …)]` на контроллерах: без токена — **401**, чужая роль — **403**;
- сервис сравнивает исполнителя или автора заявки с пользователем из токена: чужая заявка — **403**.

Клиент только прячет лишние кнопки. Запрос в обход экрана (Swagger) получает тот же 403. Полная матрица «роль × действие» — `docs/role-matrix.md`.

**Пароли (НФТ-5).** В `users.password_hash` хранится хэш `PasswordHasher` из ASP.NET Identity: PBKDF2-HMAC-SHA512, 100 000 итераций, соль у каждой строки. Base64 в строке хэша — только упаковка байтов, а не пароль.

**XSS.** Пользовательский текст (заголовок, описание) выводится только интерполяцией `{{ }}`, `v-html` в проекте нет. Описание `<script>alert(1)</script>` видно на экране как текст, окно `alert` не появляется (ЛР11).

**CORS.** API отвечает браузеру только для `http://localhost:5173`. Запрос со стороннего сайта заголовков разрешения не получает.

**Тестирование:**

| Вид | Что проверено | Где |
|-----|---------------|-----|
| Позитив по трём критериям | создание → назначение → «В ремонт» на одном `id` на экране, в Network и в SQL | `docs/acceptance-check.md`, `docs/predefense-check.md` §4, `docs/reports/lab-12.md` §3 |
| Негатив по критериям | короткий заголовок → 400; слесарь создаёт → 403; мастер назначает → 403; чужой слесарь → 403; `Closed → InProgress` → 409; без входа → 401 | Postman-коллекция, `docs/reports/lab-11.md` §4 |
| Граничные запросы | 25 запросов с ошибками и граничными значениями (битый JSON, переполнение `int`, пробелы, регистр статуса, SQL-инъекция в логине) — ни одного 500 | `docs/predefense-check.md` §3 |
| Производительность (НФТ-3) | 502 заявки: API 15–32 мс, таблица в Chrome 0,28–0,47 с при норме 2 с | `docs/predefense-check.md`, D-03 |
| Регрессия | Postman-коллекция `newman`: 27 запросов, 43 проверки, 0 ошибок | `docs/api-collection/` |

Сквозные проверки экрана выполнялись в Chrome. Firefox и Яндекс Браузер из НФТ-4 не проверялись.

- выданный токен нельзя отозвать до истечения срока;
- фильтры работают в браузере, постраничной загрузки нет;
- учебный mock после появления входа непригоден.

**Запас под ВКР** (`docs/project-proposal.md` §7). Всё перечисленное опирается на ядро «заявка — оборудование — исполнитель», сделанное в семестре:

1. Графики планово-предупредительного ремонта с автоматическим созданием плановых заявок.
2. История неисправностей единицы оборудования, классификатор причин отказов.
3. Интеграция с 1С:ТОИР / ERP: справочник оборудования, склад запчастей, списание материалов.
4. Приём сигналов от датчиков / SCADA: аварийный останов → автоматическая заявка.
5. Несколько цехов и площадок, иерархия «завод → цех → участок → оборудование», доступ по подразделениям.
6. Отчётность по простоям (MTTR, MTBF, OEE) и дашборд главного механика.

**Вывод.** Разработана трёхзвенная веб-ИС «ТОиР-Цех» (Vue 3 — ASP.NET Core — PostgreSQL). Она ведёт заявку на ремонт оборудования от создания мастером до выполнения слесарем, хранит данные в базе с ограничениями целостности и проверяет права на сервере. Три критерия приёмки ЛР1 выполняются на экране, подтверждаются запросами и строкой в базе и сохраняются после перезапуска сервера.

**Версия для демонстрации:** коммит ЛР13 с тегом `demo-lr13` в репозитории.

## Приложение А. Таблица трассировки

| Критерий ЛР1 | Где в UI | Запрос API | Где в БД |
|--------------|----------|------------|----------|
| 1. Создать | `/new` → «Создать»; строка в списке `/` с номером и `id` (`WorkOrderNew.vue`, `WorkOrderTable.vue`) | `POST /api/work-orders` → `201`, тело ответа с `id`, `number`, `"status":"New"` | `INSERT` в `work_orders`; `SELECT id, number, status FROM work_orders WHERE id = N` → `New` |
